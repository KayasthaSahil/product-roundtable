# Implementation Planning Pack

The pack turns accepted committee decisions into a clear plan for future work. It is a planning and handoff artifact only. This skill creates and validates plans and tickets; it does not implement them, dispatch coding agents, or track delivery progress.

## Design principles

1. **Ticket-first, not document-first.** The canonical planning unit is `.review/implementation/tickets/TASK-NNN.json`.
2. **One source of truth per kind of information.** Structured review records are authoritative; Markdown indexes and summaries are generated views.
3. **Read only what is needed.** A reader starts at `START-HERE.md`, selects a ticket from `tickets/INDEX.md`, then opens that ticket and only its linked references. Stack and product context live in `.review/brief/stack-profile.md` and `product-brief.md`; there is no separate pack copy.
4. **Preserve depth, remove duplication.** Technical references remain detailed where they add value. Do not repeat ticket scope, acceptance criteria, dependencies, or implementation steps in roadmap, workstream, and reference documents.
5. **No unnecessary documents.** Generate a specialist reference only when the role is active or the review contains relevant material. Generate a workstream brief only when cross-ticket coordination cannot be adequately explained by the roadmap and tickets.

## Reading workflow

1. Read `START-HERE.md`.
2. Read `PLAN/roadmap.md` for product-level outcomes, workstreams, milestones, and sequencing rationale.
3. Open `tickets/INDEX.md` to find the relevant canonical planning ticket and see its dependencies.
4. Read the selected `tickets/TASK-NNN.json`.
5. Open only the references linked by that ticket. For build/run/test commands read `.review/brief/stack-profile.md`.
6. Treat the ticket as a planning/handoff specification for a separate, authorised implementation process. This committee and skill do not execute it.

## Ticket rules

The canonical planning unit is `.review/implementation/tickets/TASK-NNN.json`. The schema lives at `.claude/skills/review-standards/schemas/ticket.schema.json`. The Chair generates tickets in P5 using `../review-committee/references/ticket-generation.md`; do not create a separate ticket-generator agent. Use `scripts/build-pack-views.py --phase P5` after ticket generation and `--phase P6` after the readiness gate to regenerate the decision log, roadmap, and ticket index from canonical JSON.

- Generate tickets only from `Accepted` or `Accepted with modifications` decisions.
- Every accepted decision must declare `implementation_required` and either link ticket IDs or provide `no_ticket_reason`.
- Tickets must be self-contained, traceable, dependency-aware, and include proposed implementation steps, test scenarios, observable acceptance criteria, and rollback considerations for a future implementation process.
- Every ticket must have a Chair-owned `quality_review` record. `PASS` with all nine checks true and no issues is required before a ticket can be handed to the owner (`AWAITING_OWNER_APPROVAL`) or marked `APPROVED` as a plan. `REVISE` maps to `REVIEW_REQUIRED`; `BLOCKED` records an unresolved planning prerequisite. No separate ticket-review agent is dispatched.
- `tickets/INDEX.md` is a generated index, never a second source of truth. It displays the recorded ticket quality-review verdict as well as planning status.
- Committee acceptance is not owner approval. Tickets remain `AWAITING_OWNER_APPROVAL` until the owner explicitly approves inclusion in the plan. That approval does not authorise implementation.
- Planning statuses describe only the planning lifecycle. Never add implementation-progress or delivery-completion statuses.

## Rules for all pack content

1. **Grounded only in the review record.** Every requirement, change, and ticket references relevant SUT-/DBT-/DEC-/WS- IDs. Do not add recommendations the committee did not decide.
2. **Plain and lean.** Explain jargon once. Avoid repeated introductions, executive summaries, or duplicated task instructions.
3. **Stack-true.** Use the verified stack profile and repository conventions.
4. **Consistent terminology.** Use `REFERENCES/terminology-and-copy.md` when present.
5. **Clear ownership.** State which file is canonical and which files are generated. Never manually edit generated indexes to fix their content.
6. Remove every `<!-- fill -->` marker. Omit irrelevant specialist references rather than creating empty files.
7. Create a `REFERENCES/*` document only when a ticket or workstream names it. Unlinked references are reported by `trace-check.py` as waste: link or delete them. User requirements live in `product-brief.md` and ticket acceptance criteria, not a separate `requirements.md`.
8. The roadmap explains outcomes, workstream grouping, milestones, sequencing rationale, and readiness conditions. Ticket JSON owns individual task scope, steps, dependencies, acceptance criteria, and verification plans.
9. A workstream brief, when needed, explains cross-ticket context only. It must not restate each ticket's implementation plan.

## Scope boundary

This skill may draft requirements, target architecture, roadmap, migration strategy, workstream context, test plans, risk registers, dependency views, and planning tickets. It must not modify product code, dispatch coding agents, execute ticket steps, create product commits, run implementation work, or record implementation completion. Ticket approval means approval of the plan only.

## Validation

Run from the repository root:

```bash
python3 .claude/skills/implementation-pack/scripts/build-pack-views.py --phase P5  # after P5 decisions, tickets and Chair quality review
python3 .claude/skills/implementation-pack/scripts/ticket-check.py          # fail-closed schema + semantic quality checks
python3 .claude/skills/implementation-pack/scripts/build-pack-views.py --phase P6  # after P6 readiness gate
python3 .claude/skills/implementation-pack/scripts/ticket-check.py
python3 .claude/skills/implementation-pack/scripts/trace-check.py
```

A missing or malformed required input is a failure, never an empty default. All ticket records must pass schema, traceability, planning-status, source-grounding, and dependency checks; tickets handed to the owner must also have a recorded Chair quality-review `PASS`. Both ticket and trace checks must pass before the review completes (P6 gate). The trace check validates the pack layout and canonical references; it does not track implementation progress.
